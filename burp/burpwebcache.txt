Enganação com cache da web
A decepção do cache web é uma vulnerabilidade que permite a um atacante enganar o cache da web para que armazene conteúdo sensível e dinâmico. Ela é causada por discrepâncias entre a forma como o servidor de cache e o servidor de origem lidam com as solicitações.

Em um ataque de engano de cache web, um atacante persuade a vítima a visitar um URL malicioso, induzindo o navegador da vítima a fazer uma requisição ambígua por conteúdo sensível. O cache interpreta erroneamente essa requisição como sendo para um recurso estático e armazena a resposta. O atacante pode então solicitar o mesmo URL para acessar a resposta armazenada em cache, obtendo acesso não autorizado a informações privadas.

Caches da Web
Um cache web é um sistema que fica entre o servidor de origem e o usuário. Quando um cliente solicita um recurso estático, a solicitação é primeiro direcionada ao cache. Se o cache não contiver uma cópia do recurso (conhecido como falha de cache), a solicitação é encaminhada para o servidor de origem, que a processa e responde. A resposta é então enviada ao cache antes de ser enviada ao usuário. O cache utiliza um conjunto predefinido de regras para determinar se deve armazenar a resposta.

Quando uma solicitação para o mesmo recurso estático for feita no futuro, o cache fornecerá a cópia armazenada da resposta diretamente ao usuário (fenômeno conhecido como acerto de cache).

Comportamento do cache, engano no cache da web
O armazenamento em cache tornou-se um aspecto comum e crucial na distribuição de conteúdo web, particularmente com o uso generalizado de Redes de Distribuição de Conteúdo (CDNs), que utilizam o cache para armazenar cópias do conteúdo em servidores distribuídos por todo o mundo. As CDNs aceleram a entrega ao fornecer o conteúdo a partir do servidor mais próximo do usuário, reduzindo os tempos de carregamento ao minimizar a distância percorrida pelos dados.

Chaves de cache
Quando o cache recebe uma requisição HTTP, ele precisa decidir se existe uma resposta em cache que possa ser fornecida diretamente ou se deve encaminhar a requisição para o servidor de origem. O cache toma essa decisão gerando uma "chave de cache" a partir de elementos da requisição HTTP. Normalmente, essa chave inclui o caminho da URL e os parâmetros de consulta, mas também pode incluir diversos outros elementos, como cabeçalhos e tipo de conteúdo.

Se a chave de cache da solicitação recebida corresponder à de uma solicitação anterior, o cache as considera equivalentes e fornece uma cópia da resposta armazenada em cache.

Regras de cache
As regras de cache determinam o que pode ser armazenado em cache e por quanto tempo. Geralmente, as regras de cache são configuradas para armazenar recursos estáticos, que normalmente não mudam com frequência e são reutilizados em várias páginas. O conteúdo dinâmico não é armazenado em cache, pois é mais provável que contenha informações confidenciais, garantindo que os usuários recebam os dados mais recentes diretamente do servidor.

Os ataques de falsificação de cache na web exploram a forma como as regras de cache são aplicadas, por isso é importante conhecer os diferentes tipos de regras, principalmente aquelas baseadas em strings definidas no caminho da URL da requisição. Por exemplo:

Regras estáticas de extensão de arquivo - Essas regras correspondem à extensão do arquivo do recurso solicitado, por exemplo, .csspara folhas de estilo ou .jspara arquivos JavaScript.
Regras de diretório estático - Essas regras correspondem a todos os caminhos de URL que começam com um prefixo específico. Elas são frequentemente usadas para direcionar diretórios específicos que contêm apenas recursos estáticos, por exemplo, /staticou /assets.
Regras de nome de arquivo - Essas regras associam nomes de arquivo específicos a arquivos de destino que são universalmente necessários para operações da web e mudam raramente, como robots.txte favicon.ico.
Os caches também podem implementar regras personalizadas com base em outros critérios, como parâmetros de URL ou análise dinâmica.

Detectando respostas em cache
Durante os testes, é crucial que você consiga identificar respostas em cache. Para isso, observe os cabeçalhos e os tempos de resposta.

Diversos cabeçalhos de resposta podem indicar que o dado está em cache. Por exemplo:

O X-Cachecabeçalho fornece informações sobre se uma resposta foi fornecida a partir do cache. Os valores típicos incluem:
X-Cache: hit- A resposta foi fornecida a partir do cache.
X-Cache: miss- O cache não continha uma resposta para a chave da solicitação, então ela foi buscada no servidor de origem. Na maioria dos casos, a resposta é então armazenada em cache. Para confirmar isso, envie a solicitação novamente para ver se o valor é atualizado para "hit".
X-Cache: dynamic- O servidor de origem gerou o conteúdo dinamicamente. Geralmente, isso significa que a resposta não é adequada para armazenamento em cache.
X-Cache: refresh- O conteúdo em cache estava desatualizado e precisava ser atualizado ou revalidado.
O Cache-Controlcabeçalho pode incluir uma diretiva que indica o uso de cache, como publicum max-agevalor superior a 0. Observe que isso apenas sugere que o recurso pode ser armazenado em cache. Nem sempre indica o uso de cache, pois o cache pode, às vezes, sobrescrever esse cabeçalho.
Se você notar uma grande diferença no tempo de resposta para a mesma solicitação, isso também pode indicar que a resposta mais rápida está sendo fornecida pelo cache.

Explorando regras de cache de extensão estática
As regras de cache geralmente têm como alvo recursos estáticos, correspondendo a extensões de arquivo comuns, como .txt .cssou .js.txt. Esse é o comportamento padrão na maioria das CDNs.

Se houver discrepâncias na forma como o cache e o servidor de origem mapeiam o caminho da URL para os recursos ou usam delimitadores, um invasor poderá criar uma solicitação para um recurso dinâmico com uma extensão estática que será ignorada pelo servidor de origem, mas visualizada pelo cache.

discrepâncias no mapeamento de caminhos
O mapeamento de URLs é o processo de associar caminhos de URL a recursos em um servidor, como arquivos, scripts ou execuções de comandos. Existem diversos estilos de mapeamento utilizados por diferentes frameworks e tecnologias. Dois estilos comuns são o mapeamento de URL tradicional e o mapeamento de URL RESTful.

O mapeamento de URL tradicional representa um caminho direto para um recurso localizado no sistema de arquivos. Aqui está um exemplo típico:

http://example.com/path/in/filesystem/resource.html

http://example.comaponta para o servidor.
/path/in/filesystem/Representa o caminho do diretório no sistema de arquivos do servidor.
resource.htmlé o arquivo específico que está sendo acessado.
Em contraste, URLs no estilo REST não correspondem diretamente à estrutura física do arquivo. Elas abstraem os caminhos dos arquivos em partes lógicas da API:

http://example.com/path/resource/param1/param2

http://example.comaponta para o servidor.
/path/resource/é um ponto final que representa um recurso.
param1e param2são parâmetros de caminho usados ​​pelo servidor para processar a solicitação.
Discrepâncias na forma como o cache e o servidor de origem mapeiam o caminho da URL para os recursos podem resultar em vulnerabilidades de engano de cache web. Considere o seguinte exemplo:

http://example.com/user/123/profile/wcd.css

Um servidor de origem que utiliza mapeamento de URL no estilo REST pode interpretar isso como uma solicitação para o /user/123/profileendpoint e retornar as informações de perfil do usuário 123, ignorando wcd.csso parâmetro por considerá-lo irrelevante.
Um cache que usa mapeamento de URL tradicional pode interpretar isso como uma solicitação de um arquivo chamado wcd.csslocalizado no /profilediretório em /user/123. Ele interpreta o caminho da URL como /user/123/profile/wcd.css. Se o cache estiver configurado para armazenar respostas para solicitações em que o caminho termina em .css, ele armazenará em cache e servirá as informações de perfil como se fosse um arquivo CSS.

discrepâncias de normalização
A normalização envolve a conversão de várias representações de caminhos de URL em um formato padronizado. Isso às vezes inclui a decodificação de caracteres codificados e a resolução de segmentos de ponto, mas isso varia significativamente de analisador para analisador.

Discrepâncias na forma como o cache e o servidor de origem normalizam a URL podem permitir que um atacante construa um payload de path traversal que seja interpretado de forma diferente por cada analisador. Considere o exemplo /static/..%2fprofile:

Um servidor de origem que decodifica caracteres de barra e resolve segmentos de ponto normalizaria o caminho /profilee retornaria informações de perfil.
Um cache que não resolve segmentos de ponto ou decodifica barras interpretaria o caminho como /static/..%2fprofile. Se o cache armazenar respostas para solicitações com o /staticprefixo , ele armazenará em cache e fornecerá as informações de perfil.
Como mostrado no exemplo acima, cada segmento de ponto na sequência de travessia do caminho precisa ser codificado. Caso contrário, o navegador da vítima o resolverá antes de encaminhar a solicitação para o cache. Portanto, uma discrepância de normalização explorável exige que o cache ou o servidor de origem decodifique os caracteres na sequência de travessia do caminho, além de resolver os segmentos de ponto.

Prevenção de vulnerabilidades de engano de cache web
Você pode tomar uma série de medidas para evitar vulnerabilidades de manipulação de cache na web:

Use sempre Cache-Controlcabeçalhos para marcar recursos dinâmicos, definidos com as diretivas no-storee private.
